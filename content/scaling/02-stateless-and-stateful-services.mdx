<Problem>
Your app works perfectly on one server. You add two more behind a load balancer for the launch. Within minutes, support tickets arrive: "I logged in, clicked *My orders*, and it asked me to log in again." Nothing is crashing. The login succeeded on `app-1`, which saved the session **in its own memory**, and the next request went to `app-2`, which has never heard of this user. The bug isn't in any one server. It's in *where the state lives*.
</Problem>

## What "state" means here

**State** is any data that must survive *between* requests. A variable that lives for one request and is gone afterwards doesn't count.

A service is **stateful** when a request only works if it reaches the particular instance that holds some data from earlier. It's **stateless** when *any* instance can handle *any* request, because everything a request needs comes with the request (a cookie, a token) or lives in a shared store all instances can reach.

The usual suspects, and where each one should move:

| State held on the instance | What breaks with 2+ instances | Where it should live |
|---|---|---|
| Login session (`HttpSession`, an in-memory map) | User appears logged out on another server | Shared session store (Redis, a DB) or a signed token |
| Shopping cart, multi-step form progress | Cart "empties" between pages | Database, or the session store |
| Uploaded files on local disk | File exists on one server only; lost on redeploy | Object storage (S3, GCS) |
| In-memory counters (rate limits, quotas) | Each server counts separately, so limits are multiplied by N | Redis (`INCR` + expiry) |
| Scheduled jobs (`@Scheduled`) | The 9 a.m. email is sent N times | One scheduler, or a distributed lock so one instance runs it |
| In-memory cache | Only costs speed: each server warms its own | Fine as an optimization, or a shared cache |
| Open WebSocket connections | Messages for a user must reach the server holding their socket | Stays stateful, plus a registry (see below) |

<MentalModel>
A stateless service is a **bank with many tellers and one central ledger**. You can walk up to any teller, because your balance isn't in the teller's head; they look it up. A stateful service is a **village shopkeeper who keeps your tab in his memory**. It works until you visit his cousin's shop, or he goes on holiday.
</MentalModel>

Stateless never means "no state". It means **state moves out of the app server into a tier built to hold it**: a database, Redis, object storage. The app servers become interchangeable.

## Why stateless wins

- **Horizontal scaling is trivial.** The load balancer can send any request anywhere, so adding capacity is just adding instances. Autoscalers can add and remove them freely.
- **Failures are cheap.** When an instance dies, you lose only the requests it was handling at that moment. Users don't notice, because their state was never on it.
- **Deploys are boring.** Rolling deploys replace instances one by one; nobody gets logged out.
- **Load stays even.** Every request can go to the least busy server (see [Load Balancing](/tracks/scaling/load-balancing)).
- **Debugging is simpler.** No "only happens when you hit server 3" bugs.

The Twelve-Factor App puts it bluntly in its *Processes* factor: "Sticky sessions are a violation of twelve-factor and should never be used or relied upon."

The cost is real too: the state now lives somewhere else, so you pay a **network hop** to read it, and that shared store becomes a component you must run, scale and keep available.

## Fix 1: Sticky sessions (session affinity)

The quickest fix: tell the load balancer to send each user back to the same server every time.

How the load balancer recognises "the same user":

- **A cookie the load balancer sets.** AWS ALB's duration-based stickiness uses a cookie named `AWSALB`; the stickiness duration is configurable from 1 second to 7 days. ALB can also follow a cookie your application sets.
- **A hash of the client IP.** NGINX's `ip_hash`, or a Kubernetes Service with `sessionAffinity: ClientIP` (default timeout 10800 seconds, i.e. 3 hours).

```yaml
# Kubernetes: same client IP → same pod
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
    - port: 80
      targetPort: 8080
  sessionAffinity: ClientIP
```

It works, and it needs zero code changes. That's why it's common in legacy apps. But it only *hides* the state; it doesn't remove it:

1. **A server dies, its users are logged out.** When the sticky target is unhealthy or deregistered, ALB simply picks a new target and re-pins the user there. Whatever was in the old server's memory is gone.
2. **Every deploy is a mass logout.** Restarting instances wipes their memory, unless you drain each server for as long as sessions last.
3. **Load goes uneven.** Users are pinned to servers, so you can't rebalance. A few heavy users on one server stay there. With IP hashing, a whole office behind one NAT IP lands on a single server.
4. **Scaling out is slow to help.** New instances only get *new* users; existing users stay pinned to the overloaded old servers.

**When stickiness is fine:** as a *performance optimization* where losing it costs only speed (for example, a warm local cache), for long-lived connections such as WebSockets, or as a temporary bridge while you move sessions out of a legacy app.

## Fix 2: Session replication

Copy every session to the other servers, so any server can serve any user. Java app servers support this directly. Tomcat's `DeltaManager` replicates every session to all the other nodes. Tomcat's own docs say this "works great for smaller clusters" but isn't recommended past about 4 nodes. Its `BackupManager` copies each session to just one backup node instead.

It removes the data loss, but every write costs network traffic to the other nodes, which limits it to small clusters. Most teams skip straight to Fix 3.

## Fix 3: A centralized session store (Redis)

Keep the **session** idea (an opaque ID in a cookie, data on the server side), but put the data in a store **every instance shares**. Redis is the usual choice: in-memory, fast, and built-in key expiry fits sessions exactly.

What happens on each request:

```text
1. Login   → app creates session id 8f2c…, writes it to Redis with a TTL (30 min)
             → Set-Cookie: SESSION=8f2c…; HttpOnly; Secure; SameSite=Lax
2. Request → any instance reads the cookie, fetches the session from Redis,
             and extends its TTL (sliding expiry)
3. Logout  → delete the key: the user is logged out on every server instantly
4. Idle    → Redis expires the key after the TTL; the next request must log in
```

In Spring Boot you don't write this yourself. Add `spring-boot-starter-session-data-redis` (as named in the Spring Boot 4 docs), and your existing `HttpSession` code now reads and writes Redis:

```properties
spring.data.redis.host=sessions.internal
spring.session.timeout=30m
# Default is Java serialization; JSON survives class changes during rolling deploys
```

Your controllers don't change. That's the point: it's the same session API, with the data simply no longer on the instance.

### The challenges it brings, and how to handle them

| Challenge | What goes wrong | How to handle it |
|---|---|---|
| **Every request now depends on Redis** | Redis down = nobody can log in or stay logged in (try it in the sim) | Run it highly available: a replica with automatic failover (Sentinel, or a managed service like ElastiCache). Monitor it like a database. |
| **An extra network hop per request** | Adds latency to every request | Same region and zone as the app; keep the session small; one lookup per request, not several |
| **Memory pressure and eviction** | If Redis is shared with your cache and evicts keys under memory pressure, it may evict *sessions*, and users are randomly logged out | Give sessions their own Redis with `maxmemory-policy noeviction`, so a full instance rejects writes loudly instead of sessions silently vanishing, and alert on memory. (The `volatile-*` policies don't protect them: sessions have a TTL, so they're eligible.) |
| **Bloated sessions** | Whole user objects or carts stored in the session → slow reads, lots of memory | Store just the user ID and a few small fields; keep real data in the database |
| **Serialization across versions** | During a rolling deploy, old and new code read the same session; Java-serialized objects can fail to deserialize after a class change | Serialize as JSON, and keep session contents simple and backwards-compatible |
| **Session fixation** | An attacker plants a known session ID before the victim logs in | Issue a new session ID at login (Spring Security does this by default) |
| **"Log me out everywhere"** | You need all sessions for a user, not just one ID | Spring Session's indexed Redis repository can find sessions by user (`findByPrincipalName`) |

## Fix 4: Put the state in the client (signed tokens)

The other way to be stateless is to have **the client carry the state**: a signed token (usually a JWT) holding the user ID and expiry. Any instance verifies the signature with a key, so there's no lookup and no shared store.

The catch is the one you saw in the sim: the server can't easily take a token back. A logged-out or banned user's token stays valid until it expires. Hence short-lived access tokens plus revocable refresh tokens. The full comparison is in [Authentication](/tracks/backend-first-principles/authentication).

## Comparing the options

| | Sticky sessions | Replication | Shared Redis store | Signed tokens |
|---|---|---|---|---|
| App servers stateless? | No | No (state copied everywhere) | **Yes** | **Yes** |
| Server dies | Its users logged out | Survives | Survives | Survives |
| Deploy | Logs users out | Survives | Survives | Survives |
| Instant logout / ban | Yes | Yes | **Yes** (delete key) | **No** (valid until expiry) |
| New dependency | None | Cluster networking | Redis, on every request | Key management |
| Load balancing | Uneven, pinned | Any | Any | Any |
| Typical fit | Legacy apps, a stopgap | Small Java clusters | Most web apps with logins | APIs, many services, mobile clients |

## Some things must stay stateful

Not everything can be stateless, and that's fine. The trick is to **keep stateful parts few, small and deliberate**:

- **Databases, Kafka, Redis itself.** The state has to live *somewhere*. In Kubernetes they run as StatefulSets with stable identity and storage (see [Kubernetes](/tracks/cloud-infra/kubernetes)), and they're operated with replication and backups.
- **WebSocket gateways.** A socket is tied to one machine. You don't make the gateway stateless; you keep a **registry** in Redis (`user → gateway`) so other services can find the right one (see [Chat System](/tracks/hld/chat-system)).
- **Partitioned caches and workers.** Route by key so each node owns a slice, and plan for nodes leaving (see [Consistent Hashing](/tracks/scaling/consistent-hashing)).

A good test for any state on an app instance: **if this instance vanished right now, would we lose only speed, or would we lose correctness?** A local cache loses only speed, which is fine. A session, a file, or a job that was supposed to run loses correctness, so it must move out.

<SeniorLens>
In design reviews, ask one question about every component: **"What happens to users if this instance disappears right now?"** If the answer is "they lose their session / upload / job", the state is in the wrong place. Sticky sessions don't change that answer. They just make it happen less often, and so are harder to test. Seniors also check the *shared store's* failure mode: if Redis goes down, do we fail closed (everyone logged out) or degrade? Decide that on purpose.
</SeniorLens>

<KeyTakeaways>
- Stateless = any instance can serve any request; state moves to a shared store or the client.
- State in server memory breaks the moment there are two servers. Sticky sessions hide it until a crash or deploy.
- A shared Redis session store keeps the session model and makes servers interchangeable; run Redis highly available and don't let it evict sessions.
- Signed tokens remove the store but make logout and bans hard.
- Ask of every instance: does losing it cost only speed, or correctness?
</KeyTakeaways>
