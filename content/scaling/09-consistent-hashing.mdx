<Problem>
You spread cache keys across 4 Redis nodes with `node = hash(key) % 4`. Traffic grows; you add a 5th node. Now `hash(key) % 5` gives a different answer for **~80% of keys**. Your cache hit rate collapses to near zero instantly, and the database gets flattened. The same problem hits sharded databases and partitioned services. **Consistent hashing** solves it: adding or removing a node moves only about `1/N` of the keys.
</Problem>

## The idea: a ring

1. Hash the **servers** onto a circle of positions (e.g. 0 to 2³²).
2. Hash each **key** onto the same circle.
3. A key belongs to the **first server clockwise** from its position.

When a server is added, it takes over only the keys between it and its predecessor. When one is removed, only its keys move to the next server. Everything else stays put.

Try adding and removing servers with virtual nodes off, then on. Compare "keys moved" for consistent hashing vs `hash % N`, and look at how even the distribution is.

<MentalModel>
A **round table** with guests (servers) sitting at random seats and dishes (keys) placed around it. Each dish belongs to the next guest clockwise. When a new guest sits down, they only take the dishes between themselves and the previous guest. Nobody else at the table is disturbed. With `% N` hashing, adding one guest is like making everyone stand up and re-pick their seats.
</MentalModel>

## Virtual nodes

With only a few servers on the ring, the gaps between them are uneven: one server may own 40% of the ring. And when a server leaves, **all** of its load goes to one neighbor.

**Virtual nodes** fix both: each physical server is placed on the ring many times (100–200 positions, by hashing `server-1#0`, `server-1#1`, …). Load averages out, and a departing server's keys spread across many others. Virtual nodes also allow **weighting**: a bigger machine gets more virtual nodes.

## Where it's used

- **Distributed caches**: Memcached clients (ketama), Redis client-side sharding.
- **Databases**: Cassandra and DynamoDB partition data across nodes on a token ring.
- **Load balancers**: hash-based routing (Envoy ring hash / Maglev) for cache locality or sticky routing.
- **CDNs**: mapping content to cache servers within a PoP.

(Redis Cluster uses a related approach: 16,384 fixed **hash slots** assigned to nodes. Moving a slot moves only its keys. Same goal, simpler bookkeeping.)

## Alternatives worth knowing

- **Rendezvous (highest random weight) hashing**: for each key, compute `hash(key, server)` for every server and pick the highest. No ring, minimal movement, simple, O(N) per lookup.
- **Jump consistent hash** (Google): tiny, fast, perfectly balanced, but servers can only be added/removed at the end (good for numbered shards).

<SeniorLens>
In interviews, consistent hashing is a means, not an end. Bring it up **when the design needs to add/remove nodes without reshuffling data** (distributed cache, sharded storage, partitioned workers), explain virtual nodes in one sentence, and immediately mention its blind spot: **hot keys**, which need separate handling (replication, local caching, key splitting).
</SeniorLens>

<KeyTakeaways>
- Modulo hashing remaps most keys when N changes; consistent hashing remaps ~1/N.
- Servers and keys share a hash ring; keys go to the next server clockwise.
- Virtual nodes balance load and spread failover.
- Used in caches, Cassandra/Dynamo, load balancers; hash slots and rendezvous hashing are cousins.
</KeyTakeaways>
