<Problem>
Your transactions are "ACID", yet two concurrent requests still produce a wrong result: a like count that's off, two doctors both leaving their shift, a double-booked meeting room. The "I" in ACID comes in **levels**, and the default level in Postgres (and most databases) permits several anomalies on purpose, for performance. Knowing exactly which ones is what lets you write correct concurrent code.
</Problem>

## The levels (SQL standard)

From weakest to strongest:

| Level | Prevents | Still allows |
|---|---|---|
| **Read Uncommitted** | (almost nothing) | Dirty reads, everything below |
| **Read Committed** (Postgres/Oracle/SQL Server default) | Dirty reads | Non-repeatable reads, phantoms, lost updates, write skew |
| **Repeatable Read** (MySQL default; snapshot isolation in Postgres) | + non-repeatable reads (+ phantoms and lost updates in Postgres) | Write skew |
| **Serializable** | Everything: result equals *some* serial order | (nothing; but aborts and retries) |

## The anomalies, by example

Step through each one below. Set the level to **Read Committed** first (the real default), then raise it.

<IsolationPlayground />

- **Dirty read**: reading another transaction's uncommitted changes.
- **Non-repeatable read**: the same row read twice in one transaction returns different values.
- **Phantom read**: the same *query* returns a different set of rows (someone inserted a matching row).
- **Lost update**: two read-modify-write cycles race; one overwrites the other.
- **Write skew**: two transactions read overlapping data, make decisions, then write *different* rows, jointly breaking an invariant.

<MentalModel>
Isolation levels are like **how much you see of colleagues' drafts in a shared office**. Read Uncommitted: you read their scribbles before they've decided (dirty). Read Committed: you only see final versions, but they may change between your glances. Repeatable Read: you get a **photocopy** of the office at the moment you started and work from that. Serializable: a supervisor checks that everyone's work could have been done one person at a time, and sends someone back to redo theirs if not.
</MentalModel>

## How databases implement it: MVCC

Postgres and InnoDB use **Multi-Version Concurrency Control**: an update creates a *new version* of the row instead of overwriting it. Each transaction sees the versions that were committed as of its **snapshot**. Readers never block writers, and writers never block readers. Old versions are cleaned up later (Postgres's `VACUUM`), which is why very long transactions cause table bloat.

## Fixing anomalies without going fully Serializable

1. **Atomic updates**: `UPDATE posts SET likes = likes + 1` instead of read-then-write. Kills most lost updates.
2. **Pessimistic locking**: `SELECT ... FOR UPDATE` locks the rows you read until commit; others wait.
3. **Optimistic locking**: a `version` column; `UPDATE ... SET ..., version = version + 1 WHERE id = ? AND version = ?`. If 0 rows are affected, someone else won, so retry. JPA's `@Version` does this.
4. **Constraints**: a `UNIQUE (room_id, slot)` index makes double booking impossible regardless of isolation.
5. **Materialize the conflict**: for write skew, lock a common row (e.g., the shift row) so both transactions contend on it.
6. **Serializable** for the critical code paths, with a **retry loop** for serialization failures.

```java
@Entity
class Product {
    @Id Long id;
    int stock;
    @Version long version;    // JPA adds "AND version = ?" to updates → OptimisticLockException on conflict
}
```

<SeniorLens>
In design interviews for booking, wallet or inventory systems, interviewers are probing exactly this. A strong answer names the anomaly ("this is a lost update" / "this is write skew"), then picks the cheapest correct tool: an atomic update, a unique constraint, optimistic locking, or Serializable with retries, and explains its contention behavior under load.
</SeniorLens>

<KeyTakeaways>
- Isolation is a spectrum; Read Committed is the common default and permits lost updates and write skew.
- MVCC gives each transaction a snapshot; readers and writers don't block each other.
- Fix races with atomic updates, locks, @Version, constraints or Serializable + retry.
- Database behavior varies. Know yours.
</KeyTakeaways>
