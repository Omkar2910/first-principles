<Problem>
Transferring $100: debit Alice, credit Bob. The server crashes between the two statements. Alice lost $100; Bob got nothing; the money vanished. Or two transfers run concurrently and read the same balance. **Transactions** are the database's answer: a group of operations that either all happen or none do, isolated from other concurrent work.
</Problem>

## ACID, decoded

| Letter | Means | Guarantee | Mechanism |
|---|---|---|---|
| **A**tomicity | All or nothing | If anything fails, all changes in the transaction are rolled back | Undo logs / MVCC + WAL |
| **C**onsistency | Valid → valid | Constraints hold before and after (FKs, UNIQUE, CHECK) | Constraints + *your* app logic |
| **I**solation | Concurrent ≈ sequential | Transactions don't see each other's in-progress work (to a degree; see next lesson) | Locks, MVCC |
| **D**urability | Committed = permanent | Survives crashes once COMMIT returns | WAL + fsync |

Note that "C" is partly **your** responsibility: the DB enforces declared constraints, but business invariants ("total of debits = total of credits") hold only if your transactions are correct.

<MentalModel>
A transaction is a **shopping cart at checkout**. You can add and remove items as you go (statements), but nothing is actually bought until you pay (COMMIT). If your card is declined (error), the whole cart is abandoned (ROLLBACK): you don't end up buying half the items.
</MentalModel>

## In SQL

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 'alice' AND balance >= 100;  -- check rows affected!
UPDATE accounts SET balance = balance + 100 WHERE id = 'bob';
INSERT INTO ledger(from_id, to_id, amount) VALUES ('alice', 'bob', 100);
COMMIT;
```

## In Spring: `@Transactional`

```java
@Service
class TransferService {
    @Transactional
    public void transfer(AccountId from, AccountId to, Money amount) {
        Account a = accounts.findForUpdate(from);     // SELECT ... FOR UPDATE
        Account b = accounts.findForUpdate(to);
        a.debit(amount);                              // throws InsufficientFunds → rollback
        b.credit(amount);
        ledger.record(from, to, amount);
    }   // commit happens here if no exception
}
```

The `@Transactional` gotchas every Spring developer hits:
- **Self-invocation**: calling a `@Transactional` method from *another method of the same class* bypasses the proxy, so no transaction starts.
- **Checked exceptions don't roll back by default**. Only `RuntimeException`/`Error` do, unless you set `rollbackFor`.
- **Only public methods** on Spring beans are proxied (by default).
- **Long transactions** hold locks: don't call HTTP services or send emails inside them.
- **Propagation**: `REQUIRED` (default) joins an existing transaction; `REQUIRES_NEW` suspends it and starts a separate one (useful for audit logs that must persist even if the main work rolls back).

## Transactions don't span systems

A DB transaction covers **one database**. If your method writes to Postgres *and* publishes to Kafka *and* calls Stripe, the transaction does not make those atomic. If the commit fails after the Kafka publish, the event is already out. That gap is handled with patterns like the **outbox**, **idempotency** and **sagas** (Track 4).

<SeniorLens>
A senior reading `@Transactional` code checks three things: **Is anything inside it a network call? Could two of these run concurrently on the same rows, and what happens? What's outside the transaction that assumes it committed?** Those questions find most real-world transaction bugs.
</SeniorLens>

<KeyTakeaways>
- Atomicity, consistency, isolation, durability: all-or-nothing, valid states, concurrency control, crash safety.
- Know the @Transactional pitfalls: self-invocation, checked exceptions, long transactions.
- A DB transaction never covers Kafka, email or other services.
</KeyTakeaways>
