<Problem>
Production was set up by clicking around the AWS console two years ago. Nobody knows exactly which security group rules exist or why. Staging "should be the same" but isn't. Rebuilding after a disaster would take weeks of archaeology. **Infrastructure as Code (IaC)** makes infrastructure **reviewable, reproducible and versioned**, just like application code.
</Problem>

## The idea

Describe the infrastructure you want in files; a tool computes the difference from reality and applies it.

```hcl
# Terraform: a private S3 bucket with encryption and versioning
resource "aws_s3_bucket" "uploads" {
  bucket = "shop-prod-uploads"
}

resource "aws_s3_bucket_versioning" "uploads" {
  bucket = aws_s3_bucket.uploads.id
  versioning_configuration { status = "Enabled" }
}

resource "aws_s3_bucket_public_access_block" "uploads" {
  bucket                  = aws_s3_bucket.uploads.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
```

```bash
terraform plan    # show exactly what will change; reviewed in the PR
terraform apply   # make it so
```

<MentalModel>
IaC is the difference between **a recipe and a dish someone once cooked**. If all you have is the dish (a manually configured environment), you can't reliably make another one, and nobody remembers why there's so much salt. With a recipe (code), anyone can recreate it, compare versions, and propose changes that others review before they're cooked.
</MentalModel>

## Tools

| Tool | Style | Notes |
|---|---|---|
| **Terraform / OpenTofu** | Declarative HCL, multi-cloud | Most widely used; state file tracks reality |
| **AWS CloudFormation / CDK** | Declarative YAML / code (TS, Java, Python) generating it | AWS-native |
| **Pulumi** | Real programming languages | Loops/abstractions in TS, Java, Go, Python |
| **Crossplane** | Kubernetes-native controllers | Infra as K8s resources, GitOps-friendly |
| **Helm / Kustomize** | Kubernetes manifests | App deployment config rather than cloud infra |

## Practices that keep IaC safe

- **Remote state with locking** (e.g. S3 + DynamoDB lock / Terraform Cloud) so two applies can't collide. State may contain secrets, so protect it.
- **Plan in CI on every PR**; apply only from the pipeline after approval. No laptop applies to production.
- **Modules** for reusable patterns (a "standard service" module: ECR repo, IAM role, log group, alarms).
- **Separate state per environment/component** to limit blast radius.
- **Drift detection**: scheduled plans to catch console changes.
- **Policy as code** (OPA/Conftest, Sentinel, Checkov, tfsec) to block public buckets, unencrypted volumes, `0.0.0.0/0` SSH rules before they're created.
- Watch for **destructive changes** in plans (`-/+ destroy and then create replacement`). A renamed resource can mean a deleted database. Use `prevent_destroy` on critical resources.

<SeniorLens>
The most important IaC skill is **reading a plan**. Seniors scan every plan for `destroy`, `replace` and IAM/network changes before approving, because a three-line diff can delete a database or open a port to the internet. Treat `terraform plan` output with the same care as a schema migration.
</SeniorLens>

<KeyTakeaways>
- Infrastructure in version control: reviewable, reproducible, auditable.
- Plan in CI, apply from pipelines, remote locked state.
- Modules for reuse, policy-as-code for guardrails, drift detection.
- Read every plan for destroys and replacements.
</KeyTakeaways>
