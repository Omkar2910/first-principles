<Problem>
"Works on my machine" happens because environments differ: Java versions, OS libraries, config, file paths. VMs fix it but are heavy (a full OS each, minutes to boot). **Containers** package your app with exactly what it needs, start in a second, and run identically from laptop to production. They're the unit of deployment for almost everything in modern infrastructure.
</Problem>

## What a container is

A container is **a regular Linux process** with:
- **Namespaces**: an isolated view of the system (its own PID tree, network stack, filesystem mounts, hostname).
- **cgroups**: limits on CPU, memory, I/O.
- A **filesystem from an image**: layered, read-only layers plus a thin writable layer.

Unlike VMs, containers **share the host kernel**. That's why they're light and fast, and why their isolation is weaker than VMs'.

<MentalModel>
VMs are **separate houses**, each with its own foundation and utilities (a full OS). Containers are **apartments in one building**: shared foundation and plumbing (the kernel), but each apartment has its own locked door, furniture and utility meters (namespaces, filesystem, cgroups). Much cheaper to build and move into, though the walls are thinner.
</MentalModel>

## Images and layers

An **image** is a stack of read-only layers, each produced by a Dockerfile instruction. Layers are cached and shared: if only your app JAR changes, only that layer is rebuilt and pushed. **Order instructions from least to most frequently changing.**

## A good Dockerfile for a Spring Boot app

```dockerfile
# ---- build stage ----
FROM eclipse-temurin:21-jdk AS build
WORKDIR /src
COPY mvnw pom.xml ./
COPY .mvn .mvn
# Cached unless pom.xml changes
RUN ./mvnw -q dependency:go-offline
COPY src src
# Assumes the jar is built as target/app.jar (<finalName>app</finalName>)
RUN ./mvnw -q package -DskipTests && \
    java -Djarmode=tools -jar target/app.jar extract --layers --destination extracted

# ---- runtime stage ----
# JRE only: smaller, fewer CVEs (or a distroless Java image)
FROM eclipse-temurin:21-jre
RUN useradd --system --uid 10001 app
# Never run as root
USER app
WORKDIR /app
COPY --from=build /src/extracted/dependencies/ ./
COPY --from=build /src/extracted/spring-boot-loader/ ./
COPY --from=build /src/extracted/snapshot-dependencies/ ./
# Only this layer changes on most commits
COPY --from=build /src/extracted/application/ ./
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75 -XX:+ExitOnOutOfMemoryError"
EXPOSE 8080
# Exec form: Java is PID 1 and receives SIGTERM
ENTRYPOINT ["java", "-jar", "app.jar"]
```

Note the comments on their own lines: Dockerfiles only treat `#` as a comment at the **start** of a line. A trailing `# comment` becomes part of the instruction's arguments, and on `ENTRYPOINT` it breaks the JSON, so Docker falls back to shell form and SIGTERM no longer reaches Java directly.

(Spring Boot can also build images without a Dockerfile: `./mvnw spring-boot:build-image` via Buildpacks.)

## Best practices checklist

- **Multi-stage builds**: build tools stay out of the runtime image.
- **Small base images** (JRE, distroless, Alpine with care): faster pulls, smaller attack surface.
- **Non-root user**; read-only filesystem where possible.
- **Pin versions** (base image tags or digests) for reproducibility.
- **No secrets in images** (they live forever in layers); inject at runtime.
- **One process per container**; log to stdout/stderr.
- **Exec-form ENTRYPOINT** (a valid JSON array) so signals reach your app (graceful shutdown).
- **Scan images** for vulnerabilities in CI (Trivy, Grype); rebuild regularly to pick up base-image patches.
- **`.dockerignore`** to keep `target/`, `.git`, local configs out of the build context.
- **Immutable tags per build** (`app:git-sha`), not just `latest`.

## Local development

`docker compose` runs your app plus dependencies (Postgres, Redis, Kafka) with one command, and Spring Boot's Docker Compose support and Testcontainers reuse the same idea for dev and tests.

<SeniorLens>
Your container image is part of your **security perimeter**. Seniors care about what's in it: every extra package is a potential CVE. A golden, regularly rebuilt base image shared across services is one of the cheapest ways to keep hundreds of services patched.
</SeniorLens>

<KeyTakeaways>
- Containers = processes + namespaces + cgroups + layered images; they share the host kernel.
- Multi-stage builds, slim bases, non-root, exec-form entrypoint, no secrets.
- Order layers by change frequency to maximize caching.
- Scan and rebuild images regularly.
</KeyTakeaways>
