<Problem>
Releases happen every two weeks on a Thursday evening. Someone builds the JAR on their laptop, copies it to servers, runs a migration by hand, and the team watches dashboards nervously. Big releases bundle 80 changes, so when something breaks, finding the culprit takes hours. Teams that deploy **small changes many times a day** have *fewer* incidents, and **CI/CD** is how they do it.
</Problem>

## Definitions

- **Continuous Integration (CI)**: every change is merged to the main branch frequently and **automatically built and tested**. Broken builds are fixed immediately.
- **Continuous Delivery**: every change that passes the pipeline is **deployable** to production at the push of a button.
- **Continuous Deployment**: every passing change **is deployed** automatically.

## A solid pipeline

```text
PR opened
  └─ CI: compile → unit tests → static analysis/lint → dependency & secret scanning
        → integration tests (Testcontainers) → build image (tag = git SHA) → image scan
        → contract/breaking-change checks (OpenAPI/proto/schema)
PR approved + merged to main
  └─ build once → push artifact to registry
        → deploy to staging (same image) → smoke tests / e2e on critical paths
        → deploy to production: canary 5% → automated metric checks → 25% → 100%
        → post-deploy verification; automatic rollback on SLO breach
```

Key principles:
- **Build once, promote the same artifact** through environments (never rebuild for prod).
- **Everything as code**: pipeline config, infrastructure, deployment manifests.
- **Fast feedback**: PR checks in under ~10 minutes, or people stop waiting for them.
- **Trunk-based development**: short-lived branches merged daily; incomplete features hidden behind **feature flags** instead of long-lived branches.
- **Database migrations** run as a pipeline step, and are backward compatible (Track 2).
- **Automated rollback** (or roll forward fast) when metrics degrade.

<MentalModel>
CI/CD is an **automated assembly line with quality inspectors**. Every small part (commit) moves down the line, gets inspected at each station (tests, scans), and is packaged identically (one artifact). Shipping is just releasing boxes that already passed every inspection. Small boxes are easy to inspect, and when one is faulty, you know exactly which box it was.
</MentalModel>

## GitOps

Instead of the pipeline pushing to the cluster, the **desired state lives in a Git repo** (manifests/Helm values with image tags). A controller in the cluster (**Argo CD**, **Flux**) continuously syncs the cluster to Git.
- Every change is a reviewed commit, so you get an audit trail for free.
- Rollback = `git revert`.
- Drift (manual `kubectl edit`) is detected and corrected.

## Measuring delivery: DORA metrics

The DORA research program (popularized by the book *Accelerate*) measures software delivery with five metrics, in two groups:

| Metric | Measures | Group |
|---|---|---|
| **Change lead time** | Commit → running in production | Throughput |
| **Deployment frequency** | How often you deploy to production | Throughput |
| **Failed deployment recovery time** | Time to recover from a deployment that needs immediate intervention (formerly "time to restore service") | Throughput |
| **Change fail rate** | Share of deployments that need immediate intervention | Instability |
| **Deployment rework rate** | Share of deployments that are unplanned fixes for production incidents | Instability |

The key finding, repeated across years of DORA research: **speed and stability go together**. Top performers do well on all five, and small, frequent changes are safer than big, rare ones. Track your own trend rather than chasing published benchmarks.

<SeniorLens>
When a team is afraid to deploy, the fix is almost never "deploy less". It's **make deploys smaller, safer and more automated**. Seniors attack the biggest source of fear first: flaky tests, manual migration steps, missing rollback, or no canary. Each one removed makes the next deploy less scary.
</SeniorLens>

<KeyTakeaways>
- CI: integrate and test every change automatically; CD: always deployable (or auto-deployed).
- Build once, promote the same artifact; everything as code.
- Trunk-based development + feature flags + backward-compatible migrations.
- DORA's five metrics: throughput (lead time, deploy frequency, recovery time) and instability (change fail rate, rework rate) improve together.
</KeyTakeaways>
