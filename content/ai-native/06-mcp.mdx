<Problem>
Every AI app wants access to the same things: GitHub, Jira, Slack, your database, your internal APIs. Without a standard, every assistant (IDE agents, chat apps, internal bots) needs its own custom integration for every system: an N×M explosion of glue code. **The Model Context Protocol (MCP)** is an open standard so you can build an integration **once** as an MCP server, and any MCP-compatible AI application can use it.
</Problem>

## The idea

MCP standardizes how AI applications discover and use **tools, data and prompts** from external systems, much like how USB standardized device connections or how the Language Server Protocol standardized editor ↔ language tooling.

Messages are **JSON-RPC 2.0**. A **host** (the AI application) runs one **client** per connected **server**:

```text
AI application (host: IDE agent, desktop chat app, your custom agent)
   └─ MCP client(s) ──JSON-RPC──▶ MCP server: GitHub
                     ──────────▶ MCP server: Postgres (read-only)
                     ──────────▶ MCP server: Your internal "orders" API
```

<MentalModel>
MCP is a **universal adapter standard for AI assistants**. Before USB, every printer, mouse and camera needed its own port and driver for each computer. With a standard plug, any device works with any computer. An MCP server is a "device" exposing a capability; any MCP-compatible assistant can plug it in.
</MentalModel>

## Core primitives

Servers can expose:
- **Tools**: functions the model can call (`create_issue`, `query_orders`, `deploy_preview`), described with JSON schemas, just like function calling.
- **Resources**: readable data/context identified by URIs (files, DB schemas, documents) that the application can pull into context.
- **Prompts**: reusable prompt templates/workflows the user can invoke.

Clients can offer one feature back to servers: **elicitation**, which lets a server ask the user for more information partway through a request (a missing parameter, a confirmation). Older revisions also had client-side **sampling** (a server borrowing the host's LLM) and **roots**; both are deprecated as of the 2026-07-28 revision.

**Transports**: **stdio** for local servers launched by the host (e.g. a CLI tool on your machine), and **streamable HTTP** for remote servers, secured with OAuth 2.x. The older HTTP+SSE transport is deprecated.

**Stateless by design** (2026-07-28 revision): there's no initialization handshake or protocol session. Every request carries its protocol version and client capabilities, and a server that needs more input returns an "input required" result that the client answers by retrying the request. That makes remote MCP servers behave like ordinary stateless HTTP services: easy to load-balance and scale horizontally.

Beyond the core, optional **extensions** add things like long-running **tasks** and interactive **MCP Apps** (UI rendered inside the conversation).

## Building a server (sketch)

Official SDKs exist for TypeScript, Python, C#, Go, Rust, Ruby, Java, Kotlin, Swift and PHP; Spring AI builds its MCP support on the Java SDK. SDKs adopt new protocol revisions on their own schedules, so check which revision yours supports. Conceptually:

```java
// Pseudocode with an MCP Java SDK / Spring AI MCP server
@Tool(description = "Look up an order's status, items and ETA by order ID (format ORD-123456). Read-only.")
public OrderSummary getOrder(@ToolParam(description = "Order ID like ORD-123456") String orderId) {
    User caller = currentUser();                       // from the authenticated MCP session
    Order o = orders.findForUser(orderId, caller)       // permissions enforced HERE
                    .orElseThrow(() -> new ToolError("Order not found or not accessible"));
    return OrderSummary.from(o);                        // concise, model-friendly result
}
```

Then register the server in your AI application's config, and the model can discover and call `getOrder`.

## Security considerations

MCP makes connecting easy, which makes **security discipline** essential:
- **Authenticate and authorize** remote servers (OAuth); tools act with the **end user's** permissions, scoped to least privilege.
- **Treat tool results as untrusted input**: content fetched by a tool (an issue comment, a web page, an email) can contain **prompt injection** attempting to hijack the agent (lesson 9).
- **Only install trusted servers**: a malicious or compromised MCP server can expose data or misdescribe tools. Review what you connect; pin versions.
- **Human confirmation**: the spec requires hosts to get the user's consent before invoking tools, and to treat tool descriptions and annotations from untrusted servers as untrusted themselves.
- Prefer **read-only** servers where possible (e.g. read-only DB roles).

<SeniorLens>
An MCP server is a **public API for AI agents**, and deserves the same rigor: authentication, authorization per user, rate limits, audit logs, versioning, and documentation (tool descriptions *are* the docs). Seniors also curate: exposing 80 tools makes agents worse; exposing 8 well-designed ones makes them better.
</SeniorLens>

<KeyTakeaways>
- MCP standardizes connecting AI applications to tools, resources and prompts.
- Hosts run clients that talk JSON-RPC to servers over stdio (local) or streamable HTTP (remote); the current revision is stateless.
- Build once, use from many AI apps.
- Security: auth, least privilege, treat tool outputs as untrusted, trusted servers only.
</KeyTakeaways>
