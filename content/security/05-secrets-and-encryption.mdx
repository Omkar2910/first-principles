<Problem>
An AWS key committed to a public GitHub repo gets abused by crypto miners **within minutes**. A database backup copied to a laptop exposes millions of records because nothing was encrypted. A former employee still has the production DB password because it hasn't been rotated in three years. **Secrets** and **encryption** are where good intentions most often meet sloppy practice.
</Problem>

## Secrets management

A **secret** is anything granting access: DB passwords, API keys, signing keys, OAuth client secrets, TLS private keys, webhook secrets.

**Rules**
1. **Never in source code, images or config files in Git.** Not even private repos (they get cloned, forked, leaked). Run secret scanning (gitleaks, GitHub secret scanning) in CI and pre-commit.
2. **Store in a secrets manager**: AWS Secrets Manager / SSM Parameter Store, GCP Secret Manager, Azure Key Vault, HashiCorp Vault. Access controlled by IAM, audited.
3. **Inject at runtime**: as env vars or mounted files from the platform (Kubernetes External Secrets / CSI driver, ECS secrets), or fetched by the app.
4. **Prefer no secret at all**: cloud IAM roles (workload identity) instead of static keys; IAM DB authentication; OIDC federation from CI to cloud instead of stored deploy keys.
5. **Rotate**: automatically where possible (Secrets Manager rotation, Vault **dynamic secrets** that are generated per service and expire).
6. **Least privilege and scoping**: one secret per service per environment.
7. **Never log secrets**; mask them in error messages and dumps.

If a secret leaks: **rotate immediately**, then investigate usage, then clean up history.

<MentalModel>
Secrets are **house keys**. You don't tape them to the front door (code), make 50 copies for everyone (shared credentials), or keep the same key for a decade (no rotation). You keep them in a **key safe with a log of who opened it** (secrets manager), give each contractor a key that only opens their room and expires (scoped, dynamic credentials), and change the locks when one goes missing.
</MentalModel>

## Encryption in transit

- **TLS everywhere**: client → edge, edge → services, services → databases and caches. Internal networks aren't automatically safe (zero trust).
- **mTLS** between services for both encryption and service identity (often via a service mesh).
- Enforce TLS on DB connections (`sslmode=verify-full` in Postgres).

## Encryption at rest

- **Storage-level**: managed disks, S3, RDS, backups encrypted with cloud KMS keys. Usually a checkbox, and it should be on by default (org policy). Protects against stolen disks/backups and some insider access.
- **Application-level / field-level**: encrypt specific sensitive fields (SSNs, bank details, health data) in the app before storing, so even DB admins and SQL-injection attackers see ciphertext. Costs: you can't query or index the plaintext easily (consider blind indexes / tokenization).

## KMS and envelope encryption

Keys are managed in a **Key Management Service** (AWS KMS, Cloud KMS, Key Vault, Vault Transit) or HSMs. The master key **never leaves** the KMS.

**Envelope encryption**:
```text
1. Ask KMS for a data key → get plaintext data key + same key encrypted under the master key
2. Encrypt your data locally with the plaintext data key (AES-256-GCM); discard plaintext key from memory
3. Store ciphertext + encrypted data key together
4. To decrypt: send the encrypted data key to KMS (IAM-checked, audited) → plaintext data key → decrypt locally
```

Benefits: large data encrypted locally (fast), master key protected and audited, **key rotation** without re-encrypting everything (re-wrap data keys), and **crypto-shredding** (delete a key to make data unreadable, useful for GDPR erasure of backups).

## Use high-level crypto libraries

Use well-reviewed libraries with safe defaults (Google **Tink**, libsodium, the AWS Encryption SDK) rather than assembling primitives yourself. Common mistakes: ECB mode, reusing IVs/nonces, no authentication (use AEAD like AES-GCM), homemade key derivation.

<SeniorLens>
Seniors aim for **"secretless" architectures**: services authenticate with platform identity (IAM roles, workload identity, mTLS certificates issued automatically), so there's nothing static to leak. Every remaining long-lived secret is treated as technical debt with an owner and a rotation schedule.
</SeniorLens>

<KeyTakeaways>
- Secrets live in a secrets manager, injected at runtime; scan repos; rotate; prefer workload identity.
- TLS everywhere, including internal hops and DB connections.
- Encryption at rest by default; field-level encryption for highly sensitive data.
- KMS + envelope encryption; use high-level crypto libraries.
</KeyTakeaways>
