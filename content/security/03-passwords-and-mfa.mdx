<Problem>
Databases leak: through SQL injection, a misconfigured backup, an insider. When yours does, what attackers get depends entirely on how you stored passwords. Plaintext or MD5 means millions of accounts compromised within hours (and on other sites, since people reuse passwords). A proper password hash means attackers get almost nothing usable. This is one of the few security decisions with a clear right answer.
</Problem>

## Hashing vs encryption

- **Encryption** is reversible with a key. Wrong for passwords: whoever gets the key gets every password.
- **Hashing** is one-way: you store `hash(password)` and compare hashes at login. You never need the original.

But not just any hash. **General-purpose hashes (MD5, SHA-1, SHA-256) are designed to be fast**, and modern GPUs compute **billions per second**, so attackers can brute-force common passwords quickly.

## Use a password hashing function

**Argon2id** (recommended), **bcrypt**, or **scrypt** (PBKDF2 when compliance requires it). They're:
- **Deliberately slow and tunable** (cost/work factor), targeting roughly 100–500 ms per hash on your servers.
- **Memory-hard** (Argon2/scrypt), which makes GPU/ASIC attacks expensive.
- **Salted**: a random per-user salt means identical passwords produce different hashes, defeating precomputed (rainbow) tables.

```java
// Spring Security
PasswordEncoder encoder = new Argon2PasswordEncoder(16, 32, 1, 1 << 16, 3);  // salt, hash, parallelism, memory KB, iterations
String stored = encoder.encode(rawPassword);          // includes algorithm params + salt
boolean ok = encoder.matches(attempt, stored);

// Or DelegatingPasswordEncoder: "{argon2}..." / "{bcrypt}..." prefixes allow upgrading algorithms over time
```

Upgrade old hashes transparently: on successful login, re-hash with the current algorithm.

<MentalModel>
A fast hash is a **lock that takes one second to try a key**: a thief with a big keyring tries millions quickly. A password hash function is a **lock that takes half a second and a heavy crank per attempt**: barely noticeable for the owner logging in once, but it makes trying millions of keys impractical. The salt means every house has a **differently shaped lock**, so one master keyring doesn't work everywhere.
</MentalModel>

## Protecting login flows

- **Rate limit and lock out progressively** per account and per IP (with care: lockouts can be abused for DoS, so prefer increasing delays and CAPTCHAs).
- **Check against breached password lists** (Have I Been Pwned k-anonymity API); NIST guidance favors this over complex composition rules.
- **Generic error messages**: "Invalid email or password", not "no account with that email" (prevents account enumeration). Same for password reset responses.
- **Password reset**: single-use, short-lived, high-entropy tokens; stored hashed; invalidate sessions after reset.
- **Constant-time comparison** for tokens (`MessageDigest.isEqual`).

## MFA and beyond passwords

- **TOTP** apps (Google Authenticator, Authy): good. **SMS** codes: better than nothing, but vulnerable to SIM swapping.
- **WebAuthn / passkeys** (FIDO2): phishing-resistant public-key credentials bound to the site's origin. The strongest option, and increasingly the default for consumer apps.
- Require MFA for admins and sensitive actions (step-up authentication).

In practice: delegate login to an **identity provider** (Okta, Auth0, Cognito, Keycloak, Entra) so password storage, MFA and passkeys are handled by specialists.

<SeniorLens>
The best password code is the code you don't write. Seniors push for a **managed identity provider** early: password storage, MFA, passkeys, breach detection, bot protection and compliance are full-time specialties. Your team's time is better spent on your product.
</SeniorLens>

<KeyTakeaways>
- Hash passwords with Argon2id/bcrypt/scrypt: slow, salted, tunable. Never encrypt or fast-hash them.
- Upgrade old hashes on login; wrap legacy hashes immediately.
- Rate limit, avoid enumeration, check breached passwords, secure reset tokens.
- MFA, preferably passkeys/WebAuthn; prefer a managed IdP.
</KeyTakeaways>
